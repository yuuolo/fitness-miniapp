## 一、结论

**能用的试点系统，工程底子不错，但运维和数据可靠性是明显短板。**

综合 6.8 / 10。功能、性能、测试覆盖都在良好水平；
真正拖后腿的是**没有监控告警、备份只有同机一份、发版全手工**，
再加上今天刚发生过一次数据被误清的事故。

当前处于**试点期**：6 个账号、2 条友圈、1 个竞赛，日活级别很低，容错空间大。
但如果要扩到几十上百人的门店，现在的运维方式撑不住。

## 五、主要风险（按严重度）

### 🔴 P0（建议一周内处理）

**1. 备份只有同机一份，等于没兜住最坏情况**
数据库和备份都在同一台机器同一块盘。磁盘坏了、机器丢了，数据和备份一起没。
今天的事故靠 11/14 的旧备份救回，但那是运气。

**2. 无法确认真实用户是否在用最新版**
1.1.0 → 1.3.1 共 13 个版本都是上传状态。如果体验版一直没设置，
真实用户看到的还是最早那一版，这十几轮改动等于没上线。

**3. 没有任何监控与告警**
服务挂了、5xx 变多、磁盘写满、备份失败——全部不会有人知道，
要等用户来投诉。

### 🟠 P1（一个月内）

**4. 单机单库，无高可用**：一次重启全站不可用；DB 无副本。
**5. 发版纯手工**：tar → scp → build → up，靠人记步骤，容易漏（今天就漏传过 Dockerfile）。
**6. 隐私合规待确认**：用了 chooseAvatar / getPhoneNumber / chooseMedia / scanCode，
小程序后台需配置「用户隐私保护指引」，否则这些能力可能被限制。
**7. 排课已下线但缺席判定仍生效**：定时任务会把未签到记缺席（3 次封禁 7 天）。
目前约课关着所以无害，**一旦重开约课又没恢复排课入口，会员会被误罚**。

### 🟡 P2（有余力再做）

8. 遗留代码：旧云开发版 `cloudfunctions/`、根 `test/`、56 个脚本里的一次性迁移脚本
9. 缺在线支付、数据导出报表、多门店/多员工分权
10. 无端到端测试流水线（自动化脚本都在本机手跑）
11. OCR 镜像 1.04 GB，可精简

## 六、值得肯定的地方

- **测试是认真的**：8 套 288 项断言，覆盖业务规则、并发占位、定时任务边界、
  报告解析的坐标配对，还带「检查器自测」（验证检查器本身有效）
- **踩坑都做了防御**：自定义 tabBar 取不到 page 变量 → 硬编码兜底；
  删角色导致 `ROLE_LEVEL.staff === undefined` 静默失效 → 加未知角色断言；
  测试误跑生产库 → 加启动拦截
- **文档跟得上**：README、架构说明、功能总览、UI 设计图、每个运维脚本都有注释
- **性能余量巨大**：现在的负载约占单核 1%，扩容到几十家店都不是瓶颈

## 七、建议的下一步（按性价比排序）

| 优先级 | 事项 | 理由 |
| --- | --- | --- |
| 1 | 设置体验版并确认能用最新版 | 十几轮改动可能对用户不可见，收益最大 |
| 2 | 备份异地化（同步到另一块盘/另一台机器/对象存储） | 唯一能兜住"机器挂了"的手段 |
| 3 | 加一个轻量监控（定时探测 /health + 失败时微信通知） | 让故障自己浮出来，而不是等投诉 |
| 4 | 一键发版脚本（构建→部署→健康检查→回滚点） | 消除手工漏步骤 |
| 5 | 小程序后台配隐私保护指引 | 合规，避免能力被限制 |
| 6 | 补数据导出（会员/体测 CSV） | 门店真实运营会要 |
| 7 | 重开约课之前，先恢复排课入口或关掉缺席判定 | 避免误罚会员 |
